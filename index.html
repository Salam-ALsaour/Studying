1. Basic Definitions — التعريفات الأساسية

Before anything else, the chapter fixes a small vocabulary that the whole course is built on. These four or five terms come back in every later chapter.

📘 Core Definitions
  • Data — known facts that can be recorded and that have an implicit meaning.
  • Database — a collection of related data; a logically coherent collection built for a specific purpose.
  • Mini-world / Universe of Discourse (UoD) — the part of the real world the database represents (e.g. students, courses and grades at a university).
  • DBMS — Database Management System: a collection of programs that lets users create and maintain a database.
  • Database System — the DBMS software together with the data itself (and sometimes the applications).
الفكرة باختصار: الـdata هي حقائق نقدر نسجّلها ولها معنى ضمني. لمّا نجمع بيانات مترابطة ومنظّمة لغرض معيّن نسمّيها database. الجزء من العالم الحقيقي اللي نمثّله (مثل: طلاب الجامعة ودرجاتهم) اسمه mini-world أو UoD. أمّا البرنامج اللي يسمح لنا ننشئ القاعدة ونديرها فهو الـDBMS. ولمّا نجمع الاثنين (البرنامج + البيانات نفسها) يصير عندنا Database System.

3. An Example: the UNIVERSITY Database — مثال الجامعة

The chapter uses one running example: a UNIVERSITY database holding information about students, courses and grades. Its records (files) are:

  • STUDENT, COURSE, SECTION, GRADE_REPORT, PREREQUISITE

Working with this database happens in three activities:

  1. Define — specify the data type of each element (string of characters, integer, etc.) and the structure of each record.
  2. Construct / Load — store the actual records for every student, course, section, etc., including the relationships among them.
  3. Manipulate — query and update the mini-world, and generate reports.
📘 Query vs Update
Query → retrieves data (read only). Example: “List the names of students who took the Database course in Fall 2008 and their grades.”
Update → changes data. Example: “Enter a grade of ‘A’ for ‘Smith’ in the Database section,” or “Create a new section for the Database course.”
مثال الجامعة هو المثال اللي بيمشي معانا طول الفصل. القاعدة فيها سجلات: STUDENT, COURSE, SECTION, GRADE_REPORT, PREREQUISITE. للتعامل معها نمرّ بثلاث مراحل: التعريف (نحدّد أنواع البيانات وبنية كل سجل)، ثم البناء/التحميل (نخزّن السجلات الفعلية والعلاقات بينها)، ثم المعالجة عن طريق query (استرجاع/قراءة فقط) وupdate (إضافة/تعديل/حذف).

4. Characteristics of the Database Approach — خصائص منهج قواعد البيانات

This is the heart of Chapter 1. First, the contrast:

Traditional File ProcessingDatabase Approach
Each user/program defines and implements its own files for one application. Leads to duplication and program-data dependence. A single repository stores data that is defined once and then accessed by many users and applications.

The database approach has four main characteristics:

① Self-Describing Nature of a Database System

The system stores a complete definition of its structure and constraints. This description is called meta-data, and it lives in the DBMS catalog (data dictionary). The catalog is used both by the DBMS software and by users who need to know the structure.

القاعدة تصف نفسها بنفسها: تخزّن وصفًا كاملًا لبنيتها وقيودها داخل ما يُسمّى catalog، وهذا الوصف اسمه meta-data. هذا يخلّي برنامج الـDBMS الواحد قادرًا يشتغل مع تطبيقات قواعد بيانات مختلفة.

② Insulation Between Programs & Data + Data Abstraction

  • Program-data independence — the structure of data files is stored in the catalog separately from the access programs, so we can change the storage structure without changing the programs.
  • Program-operation independence — an operation has two parts: an interface (name + argument types) and an implementation that can change without affecting the interface.
  • Data abstraction — a data model gives a conceptual representation of data, hiding storage and implementation details.
العزل بين البرامج والبيانات: لأن بنية البيانات مخزّنة في الـcatalog مستقلة عن البرامج، نقدر نغيّر طريقة التخزين دون ما نعدّل البرامج — وهذا اسمه program-data independence. والـdata abstraction تعني أن الـdata model يعطينا صورة مفاهيمية للبيانات ويخفي تفاصيل التخزين.

③ Support of Multiple Views of the Data

A view is a subset of the database — virtual data derived from the stored files but not explicitly stored. A multiuser DBMS lets each user/application see only the view that interests them.

④ Sharing of Data & Multiuser Transaction Processing

Many users access the database at the same time. To keep results correct, the DBMS uses:

  • Concurrency control — ensures several users updating the same data do so in a controlled manner so the result is correct.
  • OLTP (Online Transaction Processing) — supports hundreds of concurrent transactions per second.
📘 Transaction Properties (from the notes)
  • Isolation — each transaction appears to execute in isolation from other transactions.
  • Atomicity — either all the database operations in a transaction are executed, or none are.
مشاركة البيانات: عدّة مستخدمين يوصلون للقاعدة بنفس الوقت، فنحتاج concurrency control عشان لمّا أكثر من واحد يعدّل نفس البيانات تطلع النتيجة صحيحة. ومن خصائص الـtransaction: العزل isolation (كأن كل عملية تشتغل لحالها) والذرّية atomicity (إمّا تتنفّذ كل العمليات أو ولا وحدة).

5. Actors on the Scene — الفاعلون في المشهد

These are the people who use or design the database day-to-day:

  1. Database Administrators (DBA) — authorize access, coordinate & monitor use, acquire hardware/software resources.
  2. Database Designers — identify the data to be stored and choose appropriate structures to represent it.
  3. End Users — people whose jobs require access to the database.
  4. System Analysts — determine the requirements of end users.
  5. Application Programmers — implement those specifications as programs.

6. Workers Behind the Scene — العاملون خلف الكواليس

These people build the DBMS itself — they don’t use any specific database:

  1. DBMS system designers & implementers — design and implement the DBMS modules and interfaces.
  2. Tool developers — design and implement tools (design aids, performance monitors, etc.).
  3. Operators & maintenance personnel — run and maintain the hardware/software environment.
📝 Exam Tip — common trap
“Actors on the scene” use a particular database (DBA, designers, end users…). “Workers behind the scene” build the DBMS product itself (system implementers, tool developers, operators). Don’t mix them up. لا تخلط بين الفئتين.

7. Advantages of Using the DBMS Approach — مزايا استخدام منهج قواعد البيانات

  1. Controlling redundancy — via data normalization (saves storage, ensures consistency); sometimes controlled redundancy (denormalization) is used to speed up queries.
  2. Restricting unauthorized access — security & authorization subsystem, privileged software.
  3. Providing storage structures & search techniques for efficient query processing (e.g. indexes).
  4. Providing backup & recovery — the backup/recovery subsystem restores data after failure.
  5. Providing multiple user interfaces — GUIs, query languages, programming interfaces.
  6. Representing complex relationships among data.
  7. Enforcing integrity constraints — e.g. referential integrity (every SECTION must relate to a COURSE) and key / uniqueness constraints (every COURSE has a unique number).
  8. Permitting inferencing & actions using rules — triggers (a rule activated by updates) and stored procedures.
  9. Providing persistent storage for program objects (e.g. object-oriented DBMSs).
⚠️ Why NOT plain files? (Data Redundancy problems)
The file-processing approach suffers from: program-data dependence, duplication of data & effort, limited data sharing, lengthy development time, and excessive program maintenance. Storing the same data many times wastes space and causes inconsistency.
أهم المزايا للمراجعة السريعة: التحكم في التكرار controlling redundancy عبر الـnormalization (يوفّر مساحة ويمنع التضارب)؛ تقييد الوصول غير المصرّح restricting unauthorized access؛ توفير بنى تخزين وبحث فعّالة؛ النسخ الاحتياطي والاسترجاع backup & recovery؛ تعدد الواجهات؛ تمثيل العلاقات المعقّدة؛ فرض قيود التكامل integrity constraints مثل referential integrity وkey constraint؛ والقواعد والإجراءات مثل triggers. وفي المقابل، نظام الملفات التقليدي يعاني من تكرار البيانات وتبعية البرامج للبيانات وصعوبة المشاركة والصيانة.
🧾 Chapter 1 Summary — الخلاصة
A Database is a collection of related (recorded) facts. A DBMS is a generalized software package for implementing and maintaining a computerized database. The database approach is defined by being self-describing, insulating programs from data, supporting multiple views, and allowing multiuser sharing — giving advantages over plain file processing. Several categories of users (actors & workers) interact with it.

1. Data Models — نماذج البيانات

📘 Definition
A data model is a set of concepts to describe (a) the structure of a database, (b) the operations for manipulating those structures, and (c) certain constraints the database should obey.

So a data model has three parts:

  • Structure — constructs that define the database: elements with data types, groups of elements (entity, record, table), and relationships among those groups.
  • Operations — used to specify retrievals and updates by referring to the model’s constructs. They include basic operations (generic insert, delete, update) and user-defined operations (e.g. compute_student_gpa, update_inventory).
  • Constraints — restrictions on valid data that must be enforced at all times (e.g. age must be < 100).
نموذج البيانات هو مجموعة مفاهيم تصف ثلاثة أشياء: البنية (العناصر وأنواعها والمجموعات مثل entity / record / table والعلاقات بينها)، والعمليات اللي نسترجع ونعدّل فيها البيانات (أساسية مثل insert/delete/update، ومعرّفة من المستخدم مثل حساب المعدل)، والقيود اللي لازم تتحقق دائمًا (مثل: العمر أقل من ١٠٠).

📘 From the notes — conceptual model building blocks
A conceptual model uses entities (a real-world object/concept, e.g. an employee), attributes (a property that describes an entity, e.g. name or salary), and relationships (an association among two or more entities, e.g. works-on between an employee and a project). The ER model (Chapter 3) is the popular high-level conceptual model.
نقسّم النماذج إلى: مفاهيمي conceptual قريب من تصوّر المستخدم (يستخدم entities / attributes / relationships)، وفيزيائي physical يصف كيف تُخزَّن البيانات فعليًا، وتمثيلي implementation في المنتصف وتستخدمه معظم الأنظمة التجارية مثل النموذج العلائقي، وأخيرًا الذاتي الوصف self-describing اللي يدمج وصف البيانات مع قيمها مثل XML وأنظمة NoSQL.

3. Schemas vs. Instances (States) — المخطط مقابل الحالة

This distinction is one of the most exam-tested ideas in the chapter.

Database Schema (مخطط)Database State / Instance (حالة)
The description of the database: structure, data types, constraints. Specified during design; changes rarely. The actual data stored at a particular moment. Also called instance, occurrence, or snapshot. Changes constantly.
  • Schema diagram — an illustrative display of (most of) a schema.
  • Schema construct — a component/object within the schema, e.g. STUDENT, COURSE.
  • Initial state — the state when the database is first loaded.
  • Valid state — a state that satisfies the structure and constraints of the database.
📝 Exam Tip — the classic analogy
Schema = the variable declaration; State = the value at runtime. “Smith” is an instance of the entity PERSON. The schema barely changes; the state changes with every insert/update/delete.
الفرق المهم: الـschema هو وصف القاعدة (البنية، الأنواع، القيود) ويتحدّد وقت التصميم ونادرًا يتغيّر. أمّا الـstate (ويسمّى أيضًا instance / snapshot) فهو البيانات الفعلية في لحظة معيّنة ويتغيّر باستمرار. الحالة valid هي اللي تحقّق كل قيود القاعدة.

4. Three-Schema Architecture — معمارية المخططات الثلاثة

Proposed to support two key DBMS goals: program-data independence and multiple views. Its purpose is to separate user applications from the physical database. It defines three levels:

LevelSchemaDescribesModel used
InternalInternal schemaPhysical storage structures & access paths (e.g. indexes).Physical data model
ConceptualConceptual schemaStructure & constraints of the whole database for the community of users; hides physical detail.Conceptual or implementation model
ExternalExternal schemasThe various user views — each shows the part of interest and hides the rest.Same model as conceptual

Mappings connect the levels: programs refer to an external schema, the DBMS maps the request down to the internal schema for execution, then reformats the extracted data back up to match the user’s external view (e.g. formatting an SQL result for a web page).

معمارية المخططات الثلاثة هدفها فصل تطبيقات المستخدم عن التخزين الفيزيائي. ثلاثة مستويات: الداخلي internal يصف التخزين الفيزيائي ومسارات الوصول، والمفاهيمي conceptual يصف بنية القاعدة كاملة لكل المستخدمين ويخفي تفاصيل التخزين، والخارجي external هو رؤى المستخدمين (كل مستخدم يشوف اللي يهمّه). الـmappings هي اللي تترجم الطلب بين المستويات.

5. Data Independence — استقلالية البيانات

📘 Definition
Data independence = the capacity to change the schema at one level without changing the schema at the next higher level.
  • Logical data independence — change the conceptual schema without changing the external schemas or their application programs.
  • Physical data independence — change the internal schema without changing the conceptual schema (e.g. reorganizing file structures or creating new indexes to improve performance).

When a lower-level schema changes, only the mappings to the higher level need updating — the higher schemas (and the programs referring to them) stay unchanged.

📝 Exam Tip
Logical independence is harder to achieve than Physical, because changing the conceptual schema can affect more applications. Remember the direction: each level is insulated from changes below it.
استقلالية البيانات = قدرتنا نغيّر مخطط مستوى معيّن دون ما نضطر نغيّر المستوى الأعلى منه. Logical: نغيّر المخطط المفاهيمي دون التأثير على الرؤى الخارجية والبرامج. Physical: نغيّر المخطط الداخلي (مثل إعادة تنظيم الملفات أو إنشاء index) دون التأثير على المفاهيمي. عند التغيير نعدّل الـmappings فقط.

  • Loading — load data from files into the database (incl. data conversion tools).
  • Backup — back up the database periodically (e.g. to tape).
  • Reorganization — reorganize database file structures.
  • Performance monitoring — monitor database usage and performance.

8. Centralized & Client-Server Architectures — المعماريات

Centralized DBMS

Combines everything into a single system: DBMS software, hardware, application programs, and UI processing. A user may connect via a remote terminal, but all processing happens at the central site.

Two-Tier Client-Server

Specialized servers provide specialized functions: Print serverFile serverDBMS serverWeb serverEmail server. Clients access them over a network (LAN, wireless).

  • Clients — provide interfaces via a client software module; may be diskless machines, PCs or workstations connected via a network.
  • DBMS server — provides query & transaction services. Relational DBMS servers are called SQL servers / query servers / transaction servers. Clients reach them through an API using standards like ODBC (Open Database Connectivity) or JDBC (for Java).

Three-Tier Client-Server (for Web apps)

Adds an intermediate layer — the Application / Web Server — that holds the web-connectivity software and the business logic, acting as a conduit between the database server and the client.

🔐 Security benefit
In three-tier, the database server is only accessible via the middle tier — clients cannot reach it directly. Clients hold only the UI / web browser. This enhances security.
المعماريات: Centralized كل شيء في نظام واحد والمعالجة مركزية. Two-tier خوادم متخصصة (DBMS server, Web server...) والعملاء يوصلونها عبر API مثل ODBC/JDBC. Three-tier (للويب) يضيف طبقة وسطى Application Server فيها منطق العمل، وميزتها الأمان: العميل ما يقدر يوصل خادم القاعدة مباشرة.

9. Classification of DBMSs — تصنيف الأنظمة

  • By data model: relational (and object-relational), object, big-data / key-value, NoSQL.
  • Single-user (personal computers) vs. multi-user (most DBMSs).
  • Centralized (one computer, one DB) vs. distributed (multiple computers & DBs).
  • By type of access paths; and General-purpose vs. Special-purpose (e.g. airline/hotel reservation systems are special-purpose OLTP).

Cost range: from free open-source systems (MySQL, PostgreSQL) up to configurations costing millions.

🧾 Chapter 2 Summary — الخلاصة
A data model (structure + operations + constraints) gives data abstraction at conceptual, implementation, physical, or self-describing levels. We separate the schema (description) from the state (actual data). The three-schema architecture (internal / conceptual / external) plus mappings deliver logical & physical data independence. The DBMS offers DDL/DML/SDL/VDL languages, utilities, and runs on centralized, two-tier, or three-tier architectures. The DB design phases are Conceptual → Logical → Physical.

1. The Database Design Process — عملية تصميم القاعدة

Designing a database has two parallel activities: database design and applications design (the programs & interfaces — part of software engineering). This chapter focuses on conceptual database design: producing the conceptual schema using the ER model.

تصميم القاعدة له نشاطان: تصميم البيانات database design وتصميم التطبيقات applications design. هذا الفصل يركّز على التصميم المفاهيمي — نرسم الـconceptual schema باستخدام نموذج ER.

2. The COMPANY Example — مثال الشركة

The whole chapter is built on these requirements:

  • The company is organized into DEPARTMENTs. Each department has a name, number, and an employee who manages it (with a manager start date). A department may have several locations.
  • Each department controls a number of PROJECTs. Each project has a unique name, unique number, and a single location.
  • Each EMPLOYEE has SSN, address, salary, sex, birthdate. An employee works for one department but may work on several projects (storing hours/week on each). We track each employee’s direct supervisor.
  • Each employee may have several DEPENDENTs (name, sex, birthdate, relationship).

→ Four initial entity types: DEPARTMENTPROJECTEMPLOYEEDEPENDENT

4. Entity Types, Keys & Entity Sets — أنواع الكيانات والمفاتيح

  • Entity type — entities with the same attributes grouped together (e.g. EMPLOYEE, PROJECT).
  • Key attribute — an attribute whose value is unique for each entity (e.g. SSN of EMPLOYEE). May be composite (e.g. VehicleTagNumber = (Number, State)).
  • An entity type may have more than one key (CAR has VIN and license plate). In ER, each key is underlined (unlike the relational schema where only one primary key is underlined).
  • Entity set / collection — the current set of all entities of that type stored in the DB (the “state”).
📝 Exam Tip
In an ER diagram ALL candidate keys are underlined. In a relational schema only ONE (the primary key) is underlined. This subtle difference is a favorite exam question.

A relationship relates two or more entities with a specific meaning (John Smith works on ProductX). A relationship type groups relationships of the same kind (WORKS_ON between EMPLOYEE & PROJECT). The degree = number of participating entity types (binary = degree 2). A relationship set is the current state (instances) of a relationship type.

7. Constraints on Relationships — قيود العلاقات

📘 Two kinds of constraint
  • Cardinality Ratio → specifies the maximum participation: 1:1, 1:N, N:1, M:N.
  • Participation / Existence Dependency → specifies the minimum participation: total (mandatory, double line) or partial (optional, single line).
RatioMeaningCOMPANY example

8. The (min, max) Notation — صيغة الحد الأدنى والأقصى

An alternative way to state constraints. For each participation of entity E in relationship R, (min, max) says each entity e participates in at least min and at most max relationship instances. Rules: min ≤ max, min ≥ 0, max ≥ 1. Default (no constraint) = (0, N).

📝 How to read it — important!
Read the (min,max) placed next to an entity type while looking AWAY from that entity (toward the relationship). Worked examples:
  • “A department has exactly one manager; an employee manages at most one department.” → EMPLOYEE in MANAGES = (0,1); DEPARTMENT in MANAGES = (1,1).
  • “An employee works for exactly one department; a department has any number of employees.” → EMPLOYEE in WORKS_FOR = (1,1); DEPARTMENT in WORKS_FOR = (1,N).
صيغة (min,max): لكل مشاركة لكيان في علاقة، نكتب الحد الأدنى والأقصى لعدد مرات مشاركة الكيان. قاعدة القراءة: اقرأ الرقم المكتوب بجانب الكيان وأنت تنظر بعيدًا عنه نحو العلاقة. مثال: الموظف يعمل في قسم واحد بالضبط → (1,1)، والقسم فيه أي عدد من الموظفين → (1,N).

9. Recursive (Self-Referencing) Relationship — العلاقة الارتدادية

A relationship type between the same entity type playing distinct roles. Example: SUPERVISION — EMPLOYEE participates twice: once as supervisor (boss) and once as supervisee (subordinate). In the diagram each participation is labeled with a role name (role 1 / role 2) to tell them apart.

العلاقة الارتدادية recursive بين نفس الكيان لكن بأدوار مختلفة. مثال SUPERVISION: الموظف يشارك مرتين — مرة كـمشرف ومرة كـمرؤوس. نكتب role names على الخطوط للتمييز.

10. Attributes of Relationship Types — صفات العلاقات

A relationship can carry attributes. Example: HoursPerWeek of WORKS_ON — its value depends on a particular (employee, project) combination, not on either entity alone.

📌 Placement rule
Relationship attributes are mostly used with M:N relationships. In a 1:N relationship, the attribute can be moved to the entity type on the N-side.

11. Weak Entity Types — الكيانات الضعيفة

📘 Definition
A weak entity type has no key attribute of its own and is identification-dependent on another (owner) entity type. It must participate in an identifying relationship with its owner / identifying entity type. It is identified by combining its partial key with the owner entity it relates to.

Example: DEPENDENT is a weak entity. Its Name is the partial key; EMPLOYEE is the identifying (owner) entity via the identifying relationship DEPENDENT_OF. A dependent is identified by (the employee + the dependent’s first name).

🏦 Worked example from notes — BANK
Strong entities: BANK, ACCOUNT, CUSTOMER, LOAN. Weak entity: BANK-BRANCH, partial key BranchNo, identifying relationship BRANCHES. The same BranchNo may repeat under different BANKs, so the full identifier = (BANK Code + BranchNo).
الكيان الضعيف weak entity ما عنده مفتاح خاص فيه، ويعتمد في تعريفه على كيان آخر (المالك) عبر علاقة معرِّفة identifying relationship. نعرّفه بدمج المفتاح الجزئي partial key مع الكيان المالك. مثال: DEPENDENT ضعيف، مفتاحه الجزئي هو الاسم، ومالكه EMPLOYEE عبر DEPENDENT_OF. يُرسم بمستطيل ومعيّن مزدوجين.

The Enhanced Entity-Relationship (EER) Model

Textbook: Chapter 4 · Slides (Week 6)
🎯 Chapter Outline
Why EER · Subclasses, Superclasses & Inheritance · IS-A relationships · Specialization & Generalization · Constraints (predicate/attribute/user-defined; disjoint/overlapping; total/partial) · Hierarchies, Lattices & Shared Subclasses · Category / Union Type.

1. Why EER? — لماذا EER؟

The Enhanced ER (EER) model includes all the concepts of the ER model, and adds more to design more accurate schemas that reflect data properties & constraints more precisely — for complex requirements. The new concepts are: subclasses & superclasses, specialization & generalization, category / union type, and attribute & relationship inheritance.

نموذج EER يضيف على نموذج ER العادي مفاهيم تخلّينا نصمّم مخططات أدق: الأصناف الفرعية والرئيسية subclasses/superclasses، والتخصيص والتعميم specialization/generalization، والفئة/نوع الاتحاد category/union، والوراثة inheritance.

2. Subclasses, Superclasses & the IS-A Relationship

An entity type may have meaningful subgroupings. Example: EMPLOYEE can be grouped into SECRETARYENGINEERTECHNICIAN (by job), MANAGER, or SALARIED_EMPLOYEEHOURLY_EMPLOYEE (by pay method).

  • Each subgrouping is a subclass; EMPLOYEE is the superclass.
  • These are IS-A relationships: “SECRETARY IS-A EMPLOYEE”.
📘 The four golden rules of subclass membership
  1. A subclass member is the same real-world entity as a superclass member — in a distinct, specific role.
  2. An entity cannot exist as a subclass member only — it must also be a member of the superclass.
  3. A superclass member may belong to any number of subclasses (e.g. an employee who is a salaried engineering manager belongs to MANAGER + ENGINEER + SALARIED_EMPLOYEE).
  4. It is not necessary for every superclass entity to be a member of some subclass.

Attribute & Relationship Inheritance — الوراثة

A subclass entity inherits all attributes and all relationships of the superclass. So every SECRETARY has Name, SSN, … inherited from EMPLOYEE, plus its own.

الصنف الفرعي subclass يرث كل صفات وعلاقات الصنف الرئيسي superclass. العضو في الصنف الفرعي هو نفس الكيان الحقيقي لكن في دور محدّد، ولازم يكون عضوًا في الرئيسي أيضًا، وممكن ينتمي لأكثر من صنف فرعي. وليس شرطًا أن كل عضو في الرئيسي ينتمي لصنف فرعي.

3. Specialization vs. Generalization — التخصيص والتعميم

Specialization (تخصيص)Generalization (تعميم)
ProcessDefine a set of subclasses of a superclass, based on a distinguishing characteristic.Define a generalized superclass from existing entity types that share common properties.
DirectionTop-down conceptual refinement.Bottom-up conceptual synthesis.
Example{SECRETARY, ENGINEER, TECHNICIAN} is a specialization of EMPLOYEE by job type.Car, Truck, Motorcycle → generalized into Vehicle (Vehicle_ID, Brand, Model).

The subclass adds specific / local attributes (e.g. TypingSpeed of SECRETARY) and can take part in specific relationships (e.g. BELONGS_TO of HOURLY_EMPLOYEE).

🚗 Generalization example (from slides)
Before: Car(Vehicle_ID, Brand, Model, Number_of_Doors), Truck(…, Load_Capacity), Motorcycle(…, Engine_Capacity).

التخصيص specialization من أعلى لأسفل: نبدأ بصنف رئيسي ونشتق منه أصنافًا فرعية حسب خاصية مميّزة. التعميم generalization من أسفل لأعلى: نبدأ بعدة كيانات متشابهة ونجمعها في صنف رئيسي عام. الصنف الفرعي يضيف صفاته الخاصة local attributes.

  • Disjointness — Disjoint (d): an entity is in at most one subclass. Overlapping (o): an entity may be in more than one subclass.
  • Completeness — Total (double line): every superclass entity must belong to some subclass. Partial (single line): an entity may belong to none.

5. Hierarchies, Lattices & Shared Subclasses

A subclass may itself have further subclasses:

  • Hierarchy — every subclass has only one superclass → single inheritance (a tree).
  • Lattice — a subclass can have more than one superclass → multiple inheritance.
  • Shared subclass — a subclass with more than one superclass (e.g. Engineering Manager from MANAGER + ENGINEER + SALARIED_EMPLOYEE). It inherits from all predecessor superclasses.

Building direction: specialization = top-down refinement; generalization = bottom-up synthesis. In practice both are combined.

6. Category / Union Type — الفئة / نوع الاتحاد

📘 Definition
A category (or union type) is a subclass whose members are a subset of the UNION of entities from several distinct entity types (shown with a ∪ symbol). It differs from a shared subclass: a shared subclass member belongs to all its superclasses (intersection), while a category member belongs to only one of the superclasses (union). Example: an OWNER may be a PERSON, a BANK, or a COMPANY.
الفئة / نوع الاتحاد category/union هي صنف فرعي أعضاؤه مجموعة جزئية من اتحاد كيانات مختلفة (نرمز لها بـ ∪). الفرق عن shared subclass: في الـshared subclass العضو ينتمي لكل الأصناف الرئيسية (تقاطع)، أمّا في الـcategory فالعضو ينتمي لواحد فقط منها (اتحاد). مثال: المالك OWNER ممكن يكون شخصًا أو بنكًا أو شركة.
🧾 Chapter 4 Summary — الخلاصة
EER = ER + subclasses/superclasses with inheritance (IS-A). Specialization is top-down; generalization is bottom-up. Membership is predicate-, attribute-, or user-defined. Two constraints — disjoint(d)/overlapping(o) and total/partial — give four combinations. Subclasses form hierarchies (single inheritance) or lattices (multiple inheritance, via shared subclasses). A category/union type models a subset of the union of distinct entity types.

1. Relational Model Concepts — مفاهيم النموذج العلائقي

The relational model is based on the concept of a relation (= a table). Its strength comes from a formal foundation in the mathematical theory of sets. Informally, a relation looks like a table of values: rows of facts about real-world entities/relationships, with labeled columns.

📘 Informal ↔ Formal terms (memorise!)
Informal TermFormal Term

Formal Definitions — التعريفات الرسمية

  • Schema — denoted R(A₁, A₂, …, Aₙ). Example: CUSTOMER(Cust-id, Cust-name, Address, Phone#).
  • Tuple — an ordered set of values in angle brackets; a row over n attributes is an n-tuple. e.g. <632895, "John Smith", "101 Main St…", "(404) 894-2000"> is a 4-tuple. A relation is a set of such tuples.
  • Domain — a logical definition + a data type/format (e.g. USA phone numbers = (ddd)ddd-dddd). The attribute name designates the role a domain plays (the same domain Date can be both Invoice-date and Payment-date).
  • Relation state — a subset of the Cartesian product of the domains of its attributes; the current content at a point in time. e.g. dom(Cust-name) = varchar(25).
Relation = جدول، وtuple = صف، وattribute = عمود، وdomain = مجموعة القيم المسموحة لكل عمود. الـschema هو وصف الجدول R(A₁,…,Aₙ)، والـstate هو محتوى الجدول الفعلي في لحظة معيّنة وهو مجموعة جزئية من الضرب الديكارتي لنطاقات الصفات. ملاحظة: نفس الـdomain (مثل التاريخ) ممكن يلعب أدوارًا مختلفة حسب اسم الصفة.

2. Categories of Constraints — تصنيفات القيود

3. The Four Relational Integrity Constraints — قيود التكامل الأربعة

These are the explicit, schema-based constraints that must hold on all valid relation states:

  1. Key constraint — keys must be unique (no two tuples share a key value).
  2. Entity integrity — no primary-key value can be NULL.
  3. Referential integrity — between two relations; a foreign key must match an existing primary key (or be null).
  4. Domain constraint — every value must come from its attribute’s domain (or null, if allowed).

4. Keys in Depth — المفاتيح بالتفصيل

📘 The key hierarchy
  • Superkey (SK) — any set of attributes that uniquely identifies a tuple — even with unnecessary extra attributes. Formally: for any two distinct tuples t₁[SK] ≠ t₂[SK].
  • Key — a minimal superkey: removing any attribute breaks uniqueness. (No proper subset is a superkey.)
  • Candidate key — each of the (possibly several) keys of a relation.
  • Primary key (PK) — the one candidate key chosen to identify tuples; cannot be NULL; its attributes are underlined.

CAR example: CAR(State, Reg#, SerialNo, Make, Model, Year) has two candidate keys: {State, Reg#} and {SerialNo} — both are also superkeys. {SerialNo, Make} is a superkey but not a key (not minimal). Rule: any key is a superkey (not vice-versa); any set including a key is a superkey; a minimal superkey is a key. General guideline: choose the smallest candidate key as PK.

📝 Exam Tip — every relationship of keys
Primary Key ⊆ Candidate Keys ⊆ Keys ⊆ Superkeys. A key is a minimal superkey; a PK is one chosen candidate key that also can’t be null.
Superkey: أي مجموعة صفات تميّز الصف بشكل فريد (حتى لو فيها صفات زائدة). Key: superkey أصغري — لو شلت أي صفة منه يفقد التميّز. Candidate key: كل مفتاح من المفاتيح الممكنة. Primary key: المفتاح المختار للتعريف، ولا يقبل NULL، ونضع تحته خطًا. القاعدة: كل key هو superkey والعكس غير صحيح.

5. Entity Integrity — تكامل الكيان

The primary-key attributes of every relation cannot have NULL values in any tuple: t[PK] ≠ null. If the PK is composite, none of its attributes may be null. (Other non-PK attributes may still be constrained NOT NULL too.)

6. Referential Integrity — التكامل المرجعي

The only constraint that involves two relations. Tuples in the referencing relation R1 have foreign key (FK) attributes that reference the primary key of the referenced relation R2.

📘 The FK rule
The value of FK in R1 must be either:
  1. an existing PK value in R2 (t₁[FK] = t₂[PK]), or
  2. NULL — but only if FK is not part of R1’s own primary key.
Shown in a schema diagram as a directed arc from R1.FK → R2.PK.
التكامل المرجعي هو القيد الوحيد بين جدولين. الجدول R1 (المُشير) فيه مفتاح أجنبي FK يشير إلى المفتاح الأساسي PK في الجدول R2 (المُشار إليه). قيمة الـFK لازم تكون إمّا قيمة موجودة فعلًا في PK الجدول الآخر، أو NULL (بشرط ألا يكون الـFK جزءًا من المفتاح الأساسي لجدوله).

A relational database schema is the set S of all relation schemas in the database (e.g. the COMPANY schema has 6 relations connected by referential-integrity arcs).

Other Constraints

Semantic integrity constraints are business rules that can’t be expressed in the model (e.g. “max hours per employee across all projects = 56/week”). SQL-99 expresses some via CREATE TRIGGER and CREATE ASSERTION. Keys, NULL permissions, candidate keys (UNIQUE), foreign keys, and referential integrity are all expressed in the SQL CREATE TABLE statement.

7. Update Operations & Constraint Violations — عمليات التحديث وانتهاك القيود

Three update operations: INSERT, DELETE, MODIFY (UPDATE). Updates must not violate integrity constraints; they may propagate automatically to maintain integrity.

OperationCan violate…
INSERTAny constraint: Domain (wrong type), Key (duplicate key), Referential (FK with no matching PK), Entity integrity (PK is null).
DELETEOnly Referential integrity — if the deleted tuple’s PK is referenced elsewhere.
UPDATEDomain & NOT NULL always; updating PK ≈ DELETE+INSERT; updating FK may violate referential; updating an ordinary attribute → only domain.
📘 Actions on violation
  • RESTRICT / REJECT — cancel the offending operation.
  • CASCADE — propagate the change to referencing tuples.
  • SET NULL — set the referencing foreign keys to NULL.
  • Or run a user-specified error-correction routine.
One of these must be specified per foreign key during design.
ثلاث عمليات: INSERT, DELETE, UPDATE. الـINSERT ممكن ينتهك أي قيد. الـDELETE ينتهك التكامل المرجعي فقط (لو الصف مرجوع له من جدول ثاني). عند الانتهاك نختار: RESTRICT (رفض)، CASCADE (تمرير التغيير)، أو SET NULL (تصفير المفاتيح الأجنبية).

🧾 Chapter 5 Summary — الخلاصة
A relation = a set of tuples over attributes drawn from domains; its schema is the description, its state is the current content. Constraints come in three categories (implicit/explicit/semantic). The four model constraints are Key, Entity integrity (PK ≠ null), Referential integrity (FK matches PK or null), and Domain. Keys form the hierarchy super → candidate → primary. Updates (INSERT/DELETE/UPDATE) must preserve integrity, with RESTRICT / CASCADE / SET NULL as remedies.

Textbook: Chapter 6 · Slides (Week 8) + Detailed Notes

1. What is SQL? — ما هي SQL؟

SQL came from the word “SEQUEL” (from the paper “SEQUEL to SQUARE” by Chamberlin & Boyce). IBM couldn’t copyright SEQUEL, so they abbreviated it to SQL — now popularly Structured Query Language. In SQL we say table / row / column for the formal terms relation / tuple / attribute.

2. Data Definition (DDL) — تعريف البيانات

DDL is used to CREATE, DROP, and ALTER table descriptions.

CREATE TABLE & Data Types

Common data types: INTEGER, FLOAT, DECIMAL(i,j), CHAR(n), VARCHAR(n), plus DATE (yyyy-mm-dd), TIME (hh:mm:ss), TIMESTAMP (date+time), and INTERVAL (a relative value).

CREATE TABLE DEPARTMENT (
    DNAME         VARCHAR(10) NOT NULL,
    DNUMBER       INTEGER     NOT NULL,
    MGRSSN        CHAR(9),
    MGRSTARTDATE  CHAR(9) );

Specifying Constraints — PRIMARY KEY, UNIQUE, FOREIGN KEY

CREATE TABLE DEPT (
    DNAME         VARCHAR(10) NOT NULL,
    DNUMBER       INTEGER     NOT NULL,
    MGRSSN        CHAR(9),
    MGRSTARTDATE  CHAR(9),
    PRIMARY KEY (DNUMBER),
    UNIQUE      (DNAME),
    FOREIGN KEY (MGRSSN) REFERENCES EMP );
  • PRIMARY KEY — the primary key (cannot be null).
  • UNIQUE — a secondary/candidate key (no duplicates).
  • FOREIGN KEY … REFERENCES — referential integrity.
  • NOT NULL / DEFAULT — value constraints.

Referential Integrity Options

On a foreign key we can specify ON DELETE / ON UPDATE actions: RESTRICT, CASCADE, SET NULL, or SET DEFAULT.

CREATE TABLE EMP (
    ENAME    VARCHAR(30) NOT NULL,
    ESSN     CHAR(9),
    BDATE    DATE,
    DNO      INTEGER DEFAULT 1,
    SUPERSSN CHAR(9),
    PRIMARY KEY (ESSN),
    FOREIGN KEY (DNO)      REFERENCES DEPT
        ON DELETE SET DEFAULT ON UPDATE CASCADE,
    FOREIGN KEY (SUPERSSN) REFERENCES EMP
        ON DELETE SET NULL    ON UPDATE CASCADE );

DROP, ALTER, CREATE SCHEMA

DROP TABLE DEPENDENT;            -- removes the table & its definition

ALTER TABLE EMPLOYEE ADD JOB VARCHAR(12);   -- new column starts as NULL
📌 Note
A column added by ALTER TABLE ADD starts as NULL in all rows, so NOT NULL is not allowed for it. Users must then fill it via UPDATE. CREATE SCHEMA names a whole database schema.
الـDDL فيها CREATE / DROP / ALTER. نحدّد أنواع البيانات (INTEGER, VARCHAR(n), CHAR(n), DECIMAL(i,j), DATE…) والقيود: PRIMARY KEY (مفتاح أساسي)، UNIQUE (مفتاح مرشّح)، FOREIGN KEY … REFERENCES (مفتاح أجنبي). ونحدّد إجراءات التكامل المرجعي ON DELETE / ON UPDATE: RESTRICT, CASCADE, SET NULL, SET DEFAULT. العمود المُضاف بـALTER … ADD يبدأ بقيمة NULL لذلك ما يقبل NOT NULL.

3. Basic Retrieval — SELECT-FROM-WHERE

📘 The basic query block
SELECT  <attribute list>      -- projection attributes (which columns)
FROM    <table list>          -- relations needed
WHERE   <condition>;          -- Boolean selection / join condition
Comparison operators: =, <, <=, >, >=, <>.
📝 Critical distinction — set vs multiset
Unlike the formal relational model (a set), an SQL table is a multiset / bag — it allows duplicate rows. SQL does not auto-remove duplicates. Use DISTINCT, or a PRIMARY KEY/UNIQUE, to force a set. (Bag: {A,B,C,A}; order is irrelevant, but duplicates count.)

Example queries (COMPANY database)

-- Q0: birthdate & address of 'John B. Smith'  (SELECT-PROJECT)
SELECT BDATE, ADDRESS
FROM   EMPLOYEE
WHERE  FNAME='John' AND MINIT='B' AND LNAME='Smith';

-- Q1: name & address of all employees in 'Research'  (SELECT-PROJECT-JOIN)
SELECT FNAME, LNAME, ADDRESS
FROM   EMPLOYEE, DEPARTMENT
WHERE  DNAME='Research' AND DNUMBER=DNO;
-- DNAME='Research' is a SELECT condition; DNUMBER=DNO is a JOIN condition

-- Q2: projects in 'Stafford' — two join conditions
SELECT PNUMBER, DNUM, LNAME, BDATE, ADDRESS
FROM   PROJECT, DEPARTMENT, EMPLOYEE
WHERE  DNUM=DNUMBER AND MGRSSN=SSN AND PLOCATION='Stafford';
استعلام SQL أساسه ثلاث جمل: SELECT (الأعمدة المطلوبة) وFROM (الجداول) وWHERE (الشرط). الشرط ممكن يكون شرط اختيار (مثل DNAME='Research') أو شرط ربط join (مثل DNUMBER=DNO). مهم: جدول SQL يسمح بصفوف مكرّرة (multiset)، فنستخدم DISTINCT لإزالة التكرار.

Ambiguous names & Aliases — الأسماء المتشابهة والأسماء البديلة

The same attribute name may appear in different relations — qualify it: EMPLOYEE.LNAME, DEPARTMENT.DNAME. To refer to the same relation twice, use aliases (tuple variables):

-- Q8: each employee with their immediate supervisor's name (self-join)
SELECT E.FNAME, E.LNAME, S.FNAME, S.LNAME
FROM   EMPLOYEE AS E, EMPLOYEE AS S
WHERE  E.SUPER_SSN = S.SSN;
-- E = employees (supervisees), S = the same table as supervisors
-- AS can be dropped:  FROM EMPLOYEE E, EMPLOYEE S

Attribute names can be renamed too: EMPLOYEE AS E(Fn, Mi, Ln, Ssn, Bd, Addr, Sex, Sal, Sssn, Dno).

Empty WHERE & the asterisk

A missing WHERE = no condition (≡ WHERE TRUE) → all tuples. With multiple tables and no join condition, the result is the CARTESIAN / CROSS PRODUCT (all combinations — usually a mistake!). SELECT * retrieves all attributes; can be prefixed (EMPLOYEE.*).

Q1C: SELECT * FROM EMPLOYEE WHERE DNO=5;
Q10: SELECT SSN, DNAME FROM EMPLOYEE, DEPARTMENT;  -- ⚠️ Cartesian product!

4. Tables as Sets — Set Operations

SQL supports set operations (need type-compatible operands): UNION, INTERSECT, EXCEPT (difference) — these remove duplicates. Multiset versions keep duplicates: UNION ALL, INTERSECT ALL, EXCEPT ALL.

5. Pattern Matching, BETWEEN & Arithmetic

📘 LIKE / BETWEEN / arithmetic
  • LIKE — string pattern matching. % = any number of characters; _ = exactly one character.
  • BETWEEN — inclusive range.
  • Arithmetic +  –  *  / can appear in SELECT.
WHERE Address LIKE '%Houston,TX%';     -- contains the substring
WHERE Ssn     LIKE '__1__8901';        -- positions 3 and 6..9 fixed
WHERE (Salary BETWEEN 30000 AND 40000) AND Dno = 5;

-- Q13: salaries if ProductX workers get a 10% raise
SELECT FNAME, LNAME, 1.1 * SALARY AS INCREASED_SAL
FROM   EMPLOYEE, WORKS_ON, PROJECT
WHERE  SSN=ESSN AND PNO=PNUMBER AND PNAME='ProductX';

6. Ordering — ORDER BY

Sort results with ORDER BY; ASC (ascending, default) or DESC (descending). Usually placed last.

SELECT ... ORDER BY D.Dname DESC, E.Lname ASC, E.Fname ASC;

7. INSERT, DELETE & UPDATE — تعديل البيانات

Three modification commands. INSERT adds rows; UPDATE & DELETE may affect many rows that satisfy a condition. Integrity constraints are always enforced.

-- INSERT (values in CREATE-TABLE attribute order; nulls supplied explicitly)
INSERT INTO table_name VALUES (value1, value2, ...);

-- DELETE (WHERE chooses rows; missing WHERE empties the table!)
DELETE FROM table_name WHERE condition;

-- UPDATE (SET gives new values; WHERE chooses rows)
UPDATE table_name SET column_name = new_value WHERE condition;
⭐ Worked UPDATE with subquery (U6)
-- Give all employees in the 'Research' department a 10% raise
UPDATE EMPLOYEE
SET    SALARY = SALARY * 1.1
WHERE  DNO IN (SELECT DNUMBER FROM DEPARTMENT
               WHERE DNAME='Research');
On the right of =, SALARY means the old value; on the left, the new value.
📝 Exam Tip
A DELETE with no WHERE empties the entire table (but keeps its definition — unlike DROP TABLE). A DELETE may be blocked or cascade depending on referential-integrity options.
ثلاث عمليات تعديل: INSERT (تضيف صفوفًا، بنفس ترتيب الأعمدة في CREATE TABLE)، DELETE (تحذف صفوفًا حسب WHERE؛ وبدون WHERE تُفرّغ الجدول كاملًا)، وUPDATE (تعدّل قيمًا عبر SET حسب WHERE). في مثال الزيادة ١٠٪: القيمة على يمين = هي القديمة وعلى اليسار الجديدة.
🧾 Chapter 6 Summary — الخلاصة
SQL DDL (CREATE/ALTER/DROP TABLE, CREATE SCHEMA) defines tables, data types, and constraints (PRIMARY KEY, UNIQUE, FOREIGN KEY…REFERENCES, NOT NULL, DEFAULT) with referential options (RESTRICT/CASCADE/SET NULL/SET DEFAULT). Retrieval uses SELECT-FROM-WHERE; SQL tables are multisets (use DISTINCT). Features: aliases, *, set ops (UNION/INTERSECT/EXCEPT), LIKE, BETWEEN, arithmetic, ORDER BY. Modification: INSERT / DELETE / UPDATE.

1. NULL & Three-Valued Logic — القيمة الفارغة والمنطق الثلاثي

NULL has three meanings: an unknown value, an unavailable/withheld value, or a not-applicable attribute. Each NULL is considered different from every other NULL, so SQL uses three-valued logic: TRUE, FALSE, UNKNOWN. A NULL = NULL comparison is avoided — to test for null use IS NULL / IS NOT NULL.

WHERE Super_ssn IS NULL;      -- employees with no supervisor
NULL لها ٣ معانٍ: قيمة مجهولة، أو غير متاحة، أو غير قابلة للتطبيق. كل NULL تُعتبر مختلفة عن الأخرى، لذلك SQL تستخدم منطقًا ثلاثي القيم: TRUE / FALSE / UNKNOWN. لاختبار الفراغ نستخدم IS NULL أو IS NOT NULL وليس =.

2. Nested Queries — الاستعلامات المتداخلة

A nested query is a complete SELECT-FROM-WHERE block inside the WHERE clause of an outer query. The IN operator compares a value v with a set/multiset V (TRUE if v is one of them).

-- Q17: SSNs of employees working on project 1, 2, or 3 (explicit set)
SELECT DISTINCT Essn
FROM   WORKS_ON
WHERE  Pno IN (1, 2, 3);
📘 ANY / SOME / ALL
  • = ANY (= = SOME) → TRUE if v equals some value in V — equivalent to IN.
  • Combine with >, >=, <, <=, <> for richer comparisons.
  • > ALL → v must exceed every value returned by the subquery.

Queries nested with = or IN can often be collapsed into one block:

-- Q16: employees whose dependent has the same name & sex as them
SELECT E.Fname, E.Lname
FROM   EMPLOYEE AS E, DEPENDENT AS D
WHERE  E.Ssn=D.Essn AND E.Sex=D.Sex AND E.Fname=D.Dependent_name;

Tip: use tuple variables (aliases) for all tables to avoid ambiguity; put tuples of values in parentheses when comparing.

3. Correlated Nested Queries — EXISTS / NOT EXISTS

A correlated nested query is evaluated once for each tuple of the outer query (the inner query references the outer tuple). The EXISTS function checks whether the subquery result is non-empty (Boolean). UNIQUE(Q) returns TRUE if Q has no duplicates.

-- Q7: names of managers who have at least one dependent
SELECT Fname, Lname
FROM   EMPLOYEE
WHERE  EXISTS (SELECT * FROM DEPENDENT  WHERE Ssn = Essn)
  AND  EXISTS (SELECT * FROM DEPARTMENT WHERE Ssn = Mgr_Ssn);

-- Q6: names of employees who have NO dependents
SELECT Fname, Lname
FROM   EMPLOYEE
WHERE  NOT EXISTS (SELECT * FROM DEPENDENT WHERE Ssn = Essn);
الاستعلام المتداخل المترابط correlated يُنفَّذ مرة لكل صف في الاستعلام الخارجي. EXISTS تتحقق هل نتيجة الاستعلام الداخلي غير فارغة، وNOT EXISTS العكس. مثال شائع: الموظفون الذين ليس لديهم معالون نستخدم NOT EXISTS.

4. Joined Tables & Outer Joins — الجداول المرتبطة

SQL lets you place a joined table directly in the FROM clause.

     FROM (EMPLOYEE NATURAL JOIN
           (DEPARTMENT AS DEPT (Dname, Dno, Mssn, Msdate)))

-- LEFT OUTER JOIN — every employee, even those with no supervisor

FROM   EMPLOYEE AS E LEFT OUTER JOIN EMPLOYEE AS S
       ON E.Super_ssn = S.Ssn;

5. Aggregate Functions — الدوال التجميعية

Summarize many tuples into a single value: COUNT, SUM, MAX, MIN, AVG. NULL values are discarded before aggregation. Results can be renamed with AS. (SOME/ALL also act on Booleans: SOME ≈ OR, ALL ≈ AND.)

SELECT COUNT(*) AS Total, AVG(Salary) AS AvgPay, MAX(Salary), MIN(Salary)
FROM   EMPLOYEE;

6. GROUP BY & HAVING — التجميع والتصفية

📘 The rules
  • GROUP BY partitions the relation into subgroups by the grouping attribute(s), then applies the aggregate to each group independently. The grouping attribute(s) must appear in the SELECT clause. A NULL grouping value forms its own group.
  • HAVING selects/rejects entire groups (a condition on the aggregate).
-- Q24: count & average salary per department
SELECT Dno, COUNT(*), AVG(Salary)
FROM   EMPLOYEE
GROUP BY Dno;

-- Q26: projects with MORE THAN two employees
SELECT Pnumber, Pname, COUNT(*)
FROM   PROJECT, WORKS_ON
WHERE  Pnumber = Pno
GROUP BY Pnumber, Pname
HAVING COUNT(*) > 2;

-- Customers per country (>10 only), busiest first, excluding USA
SELECT COUNT(Id), Country
FROM   Customer
WHERE  Country <> 'USA'
GROUP BY Country
HAVING COUNT(Id) >= 9
ORDER BY COUNT(Id) DESC;
📝 Exam Tip — WHERE vs HAVING
WHERE filters tuple by tuple before grouping; HAVING filters whole groups after grouping. Logical evaluation order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY.
GROUP BY تقسّم الجدول لمجموعات حسب صفة (أو صفات) التجميع، وتطبّق الدالة على كل مجموعة. الصفة المُجمَّع عليها لازم تظهر في SELECT. HAVING تصفّي المجموعات كاملة. الفرق المهم: WHERE تصفّي صفًا صفًا قبل التجميع، وHAVING تصفّي المجموعات بعد التجميع. ترتيب التنفيذ المنطقي: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY.

8. Assertions, Triggers & Views — القيود والمشغّلات والرؤى

📘 Semantic constraints & actions (SQL-99)
  • CREATE ASSERTION — declares a semantic constraint (a business rule) using a CHECK condition that must always hold across the database.
  • CREATE TRIGGER — specifies an automatic action (Event–Condition–Action): when an event (INSERT/UPDATE/DELETE) occurs and a condition holds, an action runs.
  • View — a virtual table derived from base tables (full treatment in Unit 11).
-- Assertion: every employee's salary ≤ their department manager's salary
CREATE ASSERTION SALARY_CONSTRAINT
CHECK ( NOT EXISTS ( SELECT * FROM EMPLOYEE E, EMPLOYEE M, DEPARTMENT D
                     WHERE E.Salary > M.Salary
                       AND E.Dno = D.Dnumber
                       AND D.Mgr_ssn = M.Ssn ) );
ASSERTION تُعبّر عن قيد دلالي (قاعدة عمل) عبر شرط CHECK يجب أن يتحقق دائمًا. TRIGGER يحدّد إجراءً تلقائيًا (حدث–شرط–فعل) يُنفَّذ عند INSERT/UPDATE/DELETE. أمّا الـViews (الجداول الافتراضية) فلها شرح كامل في الوحدة ١١.

The Relational Algebra

Textbook: Chapter 8 · Slides (Week 11) + Notes
🎯 Chapter Outline

1. Overview — نظرة عامة

Relational algebra is the basic set of operations for the relational model. Each operation takes one or more relations and produces a new relation — so the result can be fed into another operation (the algebra is “closed”). A sequence of operations is a relational-algebra expression.

GroupOperations
UnarySELECT (σ), PROJECT (π), RENAME (ρ)

💡 Origin of “Algebra”
The word algebra comes from al-jabr, the book by Muhammad ibn Musa al-Khwarizmi (~800–847 CE). He called variables “shay” (Arabic for “thing”), transliterated in Spain as “xay” → abbreviated to x. The word algorithm also comes from “al-Khwarizmi”.

2. SELECT (σ) — العملية الأحادية: الاختيار

SELECT picks a subset of the rows (horizontal partitioning) that satisfy a Boolean condition. Form: σ<condition>(R).

σ DNO = 4 (EMPLOYEE)            -- employees in department 4
σ SALARY > 30000 (EMPLOYEE)    -- employees earning over 30,000
📘 Properties of SELECT
  • Result has the same schema as R; |result| ≤ |R|.
  • Commutative: σ_c1(σ_c2(R)) = σ_c2(σ_c1(R)).
  • A cascade can be merged with AND: σ_c1(σ_c2(R)) = σ_(c1 AND c2)(R).

3. PROJECT (π) — الإسقاط

PROJECT keeps certain columns (vertical partitioning) and discards the rest. Form: π<attribute list>(R). Because the result is a set, PROJECT removes duplicate tuples.

π LNAME, FNAME, SALARY (EMPLOYEE)
📘 Properties of PROJECT
|result| ≤ |R|; if the attribute list includes a key, then |result| = |R| (no duplicates removed). PROJECT is not commutative.
SELECT (σ) تختار صفوفًا تحقّق شرطًا (تقسيم أفقي)، والنتيجة بنفس أعمدة الجدول. PROJECT (π) تختار أعمدة (تقسيم رأسي) وتحذف الصفوف المكرّرة لأن النتيجة مجموعة set. لو القائمة فيها مفتاح فلن يُحذف أي صف.

4. Expressions, Intermediate Naming & RENAME (ρ)

You can write one nested expression, or break it into steps using the assignment arrow ← to name intermediate relations:

-- Single expression:
π FNAME, LNAME, SALARY ( σ DNO=5 (EMPLOYEE) )

-- Step-by-step (equivalent):
DEP5_EMPS ← σ DNO=5 (EMPLOYEE)
RESULT    ← π FNAME, LNAME, SALARY (DEP5_EMPS)

RENAME (ρ) changes the relation name and/or the attribute names: ρ_S(B1,…,Bn)(R).

5. Set-Theory Operations — عمليات نظرية المجموعات

📘 Type compatibility
UNION, INTERSECTION, DIFFERENCE require the two relations to be type compatible: same number of columns, and corresponding columns of compatible type. (CARTESIAN PRODUCT does not.)
OpResultExample (R={(1,A),(2,B),(3,C)}, S={(2,B),(3,C),(4,D)})
UNION (∪)All tuples in R or S; duplicates removed.R∪S = {(1,A),(2,B),(3,C),(4,D)}
INTERSECTION (∩)Tuples in both R and S.R∩S = {(2,B),(3,C)}
DIFFERENCE (−)Tuples in R but not in S.R−S = {(1,A)}
📘 Properties
∪ and ∩ are commutative & associative. DIFFERENCE is not commutative: R − S ≠ S − R in general.

6. CARTESIAN PRODUCT (×) — الضرب الديكارتي

Combines every tuple of R with every tuple of S. Result has n + m attributes and nR × nS tuples. Operands need not be type compatible. On its own it is usually not meaningful — it becomes useful when followed by a SELECT:

FEMALE_EMPS     ← σ SEX='F' (EMPLOYEE)
EMPNAMES        ← π FNAME, LNAME, SSN (FEMALE_EMPS)
EMP_DEPENDENTS  ← EMPNAMES × DEPENDENT          -- every combination (not meaningful)
ACTUAL_DEPS     ← σ SSN=ESSN (EMP_DEPENDENTS)   -- keep only real pairs
RESULT          ← π FNAME, LNAME, DEPENDENT_NAME (ACTUAL_DEPS)

7. JOIN (⋈) — الربط

JOIN = CARTESIAN PRODUCT followed by SELECT, combined into one operation. It combines related tuples from two relations: R ⋈<join condition> S. The result keeps only tuples satisfying the condition (so generally fewer than nR × nS).

-- Name of the manager of each department
DEPT_MGR ← DEPARTMENT ⋈ MGRSSN=SSN EMPLOYEE
VariantDefinition
Theta-joinGeneral case — the condition (θ) can be any Boolean expression (e.g. R.Ai < S.Bj).
EQUIJOINJoin using only equality (=). The result has one or more pairs of columns with identical values (the matching columns; names need not match).
NATURAL JOIN (*)Like EQUIJOIN but removes the superfluous duplicate column. Requires the join attributes to have the same name in both relations (rename first if not).
-- Natural join on DNUMBER (only attribute with the same name)
DEPT_LOCS ← DEPARTMENT * DEPT_LOCATIONS
JOIN (⋈) = CARTESIAN PRODUCT ثم SELECT في عملية واحدة، يجمع الصفوف المترابطة. EQUIJOIN يستخدم المساواة فقط ويُبقي عمودين متطابقي القيم. NATURAL JOIN (*) مثل EQUIJOIN لكن يحذف العمود المكرّر الزائد، ويشترط تطابق اسم صفة الربط في الجدولين. والحالة العامة theta-join تسمح بأي شرط منطقي.

8. DIVISION (÷) — القسمة

📘 Definition
R(Z) ÷ S(X) where X ⊆ Z and Y = Z − X; the result is T(Y). A tuple t is in T if — for every tuple in S — there is a matching tuple in R combining t’s Y-values with that S-tuple’s X-values. In plain terms: DIVISION finds items in R that are related to all items in S.

Classic query: “Names of employees who work on all the projects that John Smith works on”:

SMITH        ← σ FNAME='John' AND LNAME='Smith' (EMPLOYEE)
SMITH_PNOS   ← π PNO (WORKS_ON ⋈ ESSN=SSN SMITH)      -- John's projects
SSN_PNOS     ← π ESSN, PNO (WORKS_ON)                  -- all (emp, project) pairs
SSNS(SSN)    ← SSN_PNOS ÷ SMITH_PNOS                   -- employees on ALL his projects
RESULT       ← π FNAME, LNAME (SSNS * EMPLOYEE)
القسمة (÷) تجيب العناصر في R المرتبطة بـكل عناصر S. المثال الكلاسيكي: «الموظفون الذين يعملون على كل المشاريع التي يعمل عليها جون سميث» — نقسّم أزواج (الموظف، المشروع) على مجموعة مشاريع جون سميث.

9. Additional Operations — عمليات إضافية

  • OUTER JOINs (LEFT / RIGHT / FULL) — keep unmatched tuples too, padding the missing side with NULL (vs the inner JOIN which drops unmatched tuples).
  • OUTER UNION — unions two partially-compatible relations.
  • AGGREGATE functions (ℱ) — COUNT, SUM, MAX, MIN, AVG, with optional grouping attributes, to compute summaries.

Unit 10 · Design Theory

Functional Dependencies & Normalization

Slides (Week 12) + Notes (Textbook Ch 10) + Spurious-Tuples handout
🎯 Chapter Outline
Why normalize · Update anomalies · Spurious tuples & lossless join · Functional Dependencies · Armstrong’s inference rules & closure · Keys (prime/non-prime) · 1NF · 2NF · 3NF · BCNF.

1. Why Normalize? — لماذا التطبيع؟

Normalization avoids four problems: (1) mixing attributes of distinct real-world entities, (2) redundant information and update anomalies, (3) too many NULL values, (4) generation of spurious tuples.

📘 The three update anomalies
  • Insertion anomaly — cannot add data because other data is missing (e.g. can’t insert a project unless an employee is assigned to it).
  • Deletion anomaly — deleting one fact unintentionally loses other facts (deleting the last employee on a project loses the project).
  • Modification anomaly — redundant data must be changed in many rows; a partial update causes inconsistency (renaming a project must change all 100 employee rows).
التطبيع normalization هو تنظيم البيانات لتقليل التكرار وتحسين التكامل، عبر تقسيم الجداول الكبيرة لجداول أصغر مترابطة. يعالج ثلاثة شذوذات: الإدخال (ما نقدر نضيف بسبب غياب بيانات أخرى)، الحذف (نفقد بيانات مهمة عند الحذف)، التعديل (نضطر نعدّل في أماكن كثيرة فيحصل تضارب).

2. Spurious Tuples & Lossless Join — التابع الزائف والربط بلا فقد

A spurious tuple is a false row that appears when badly-decomposed tables are joined (often a Cartesian product when there’s no proper common attribute). A decomposition must be lossless (non-additive): re-joining the pieces gives exactly the original relation — no extra rows. A lossy decomposition produces spurious tuples.

⚠️ Guideline 4
Design schemas so that joins use (foreign key, primary key) equality. The lossless-join property cannot be sacrificed; dependency preservation is less strict and may sometimes be sacrificed.
التابع الزائف spurious tuple هو صف خاطئ يظهر عند ربط جداول مُفكَّكة بشكل سيّئ (غالبًا بسبب lossy decomposition أو غياب صفة مشتركة). التفكيك الصحيح لازم يكون بلا فقد lossless: إعادة الربط تعطي الجدول الأصلي تمامًا دون صفوف زائدة.

3. Functional Dependencies (FDs) — الاعتماديات الوظيفية

📘 Definition
A functional dependency X → Y holds if whenever two tuples agree on X they must agree on Y (X uniquely determines Y). Formally: if t1[X]=t2[X] then t1[Y]=t2[Y]. FDs come from real-world meaning. If K is a key, then K → all attributes. 
SSN → ENAME
PNUMBER → {PNAME, PLOCATION}
{SSN, PNUMBER} → HOURS        -- needs BOTH attributes together
{StudentID, CourseID} → Grade -- neither alone determines Grade

Armstrong’s Inference Rules — قواعد آرمسترونغ

📘 Sound & complete set
  • IR1 Reflexive: if Y ⊆ X then X → Y.
  • IR2 Augmentation: if X → Y then XZ → YZ.
  • IR3 Transitive: if X → Y and Y → Z then X → Z.
Derived: Decomposition (X→YZ ⟹ X→Y, X→Z), Union (X→Y, X→Z ⟹ X→YZ), Pseudotransitivity (X→Y, WY→Z ⟹ WX→Z).

Closure F⁺ = all FDs inferable from F. Attribute closure X⁺ = all attributes determined by X. Two FD sets are equivalent if F⁺ = G⁺ (each covers the other). A minimal set has single-attribute RHS, no removable FD, and no reducible LHS.

Keys: Prime vs Non-prime

A prime attribute is a member of some candidate key; a non-prime (nonkey) attribute belongs to no candidate key. Normal forms are defined in terms of these.

X → Y تعني أن X يحدّد Y بشكل فريد. قواعد آرمسترونغ: الانعكاس reflexive، الزيادة augmentation، التعدّي transitive — ومنها نشتق التحليل والاتحاد. X⁺ هو إغلاق الصفات (كل ما تحدّده X). الصفة الأولية prime جزء من مفتاح مرشّح، وغير الأولية ليست كذلك.

4. The Normal Forms — الأشكال الطبيعية

FormRule
1NFAll values atomic — no repeating groups, multivalued, composite, or nested attributes.
2NFIn 1NF + every non-prime attribute is fully functionally dependent on the PK (no partial dependency on part of a composite key).
3NFIn 2NF + no transitive dependency (no non-key attribute depending on another non-key attribute).
BCNFFor every FD X → A, X is a superkey. Stronger than 3NF (“3.5NF”).

Each form is strictly stronger: every BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF. Some relations are 3NF but not BCNF.

1NF — make values atomic

-- UNF (repeating group):           -- 1NF (one value per cell):
StudentID | Borrowed books           StudentID | Borrowed book
C45       | B33, B44, B55      →      C45       | B33
                                      C45       | B44
                                      C45       | B55

2NF — remove partial dependencies

Student-Course(StudentID, CourseID, CourseName, Instructor), PK = {StudentID, CourseID}. Here CourseID → CourseName, Instructor — a partial dependency (depends only on part of the key). Decompose:

Course(CourseID, CourseName, Instructor)
Enrollment(StudentID, CourseID)

3NF — remove transitive dependencies

If A → B and B → C then A → C (transitive). Example tournament table, PK = {Tournament, Year}: (Tournament,Year) → Winner and Winner → DOB, so DOB is transitively dependent. Decompose:

Wins(Tournament, Year, Winner)
Player(Winner, DOB)

BCNF — every determinant is a superkey

3NF-but-not-BCNF example, PK = {Project, Branch}: FDs {Project,Branch} → Manager and Manager → Branch. Manager is a determinant but not a superkey → BCNF violation. Decompose on the offending FD:

R1(Manager, Branch)      -- from Manager → Branch
R2(Project, Manager)
📝 Exam Tip — the ladder
1NF = atomic · 2NF = no partial dependency · 3NF = no transitive dependency · BCNF = every determinant is a superkey. To move up a level you decompose (project) the offending dependency into its own relation with a copy of its determinant.
سُلّم الأشكال: 1NF قيم ذرّية · 2NF لا اعتمادية جزئية · 3NF لا اعتمادية متعدّية · BCNF كل محدِّد determinant لازم يكون superkey. للانتقال لمستوى أعلى نفكّك الاعتمادية المخالفة في جدول مستقل مع نسخة من محدِّدها. كل شكل أقوى من السابق.
🧾 Chapter 10 Summary — الخلاصة
Normalization removes redundancy and the insert/delete/modify anomalies, and avoids spurious tuples (decompositions must be lossless). FDs (X→Y) plus Armstrong’s rules and closure formalize “good” design. The ladder: 1NF (atomic) → 2NF (no partial) → 3NF (no transitive) → BCNF (every determinant a superkey).

Database Views, Authorization & Security

Textbook: Slides (Week 10)
🎯 Chapter Outline
Aspects of database security · Privileges (GRANT / REVOKE) · Views (virtual tables) · View updatability · Combining views & privileges · Integrity.

1. Database Security — أمن قواعد البيانات

Security is about controlling access to information. Many layers matter:

  • Legal issues — data-protection laws, consent, retention/deletion policies.
  • Physical security — protect servers/backups from theft, disasters, unauthorized access.
  • OS / Network security — firewalls, OS patches, Intrusion Detection Systems.
  • Policies & protocols — access-control policies, reviews, training.
  • Encryption & passwords — data-at-rest & data-in-transit encryption, strong passwords + MFA, lockout.
  • DBMS security — each user has an account (username/password); the DBMS verifies it and checks permissions when a user retrieves data, modifies data, or modifies structure.
الأمن هو التحكم في الوصول للمعلومات، وله طبقات: قانونية، فيزيائية، أمن نظام التشغيل والشبكة، السياسات، التشفير وكلمات المرور، وأمن الـDBMS نفسه (لكل مستخدم حساب وصلاحيات يتحقّق منها النظام).

2. Privileges — الصلاحيات (GRANT / REVOKE)

SQL controls access with privileges: SELECT, INSERT, UPDATE, DELETE. The owner (creator) of an object has all privileges and can grant them to others. This enforces the principle of least privilege — users get only what their role needs.

GRANT SELECT, INSERT ON employees TO Ali;     -- give privileges
REVOKE SELECT, INSERT ON employees FROM Ali;  -- take them back
📌 Revoke behaviour
If a user got the same privilege from several grantors, everyone must revoke before it’s gone. Also, all privileges dependent on a revoked one are revoked too (cascading).

3. Views (Virtual Tables) — الرؤى

Privileges work at the table level: you can restrict by column, but not by row. Views solve this. A view is a derived/virtual table = the result of a stored SELECT, treated like a table. Its value depends on the base tables (changes propagate both ways).

CREATE VIEW vw_emp_dept AS
SELECT e.emp_id, e.name, d.dept_name, e.salary
FROM   Employees e JOIN Departments d ON e.dept_id = d.dept_id;
📘 View updatability
Updatable when defined on a single table and containing a primary/candidate key. Not updatable when defined over multiple tables via a join, or containing aggregates / GROUP BY.
⭐ Views + privileges (customized access)
To restrict someone’s access to a table: (1) create a view showing only what they need, (2) grant privileges on the view, (3) revoke their privileges on the underlying table.
الصلاحيات تشتغل على مستوى الجدول (ممكن نقيّد بالأعمدة لكن ليس بالصفوف). الحل هو الـView: جدول افتراضي ناتج من SELECT مخزّن. يمكن تحديث الرؤية إذا كانت على جدول واحد وتحتوي مفتاحًا، ولا يمكن تحديثها إذا كانت على عدة جداول أو فيها aggregate/GROUP BY. لتخصيص الوصول: ننشئ view + نمنح صلاحيات عليها + نسحب الصلاحيات عن الجدول الأصلي.
🧾 Chapter 11 Summary — الخلاصة
Security spans legal, physical, OS/network, policy, encryption, and DBMS layers. SQL privileges (SELECT/INSERT/UPDATE/DELETE) are managed with GRANT/REVOKE (revokes cascade). Views are virtual tables that enable row-level customized access; combine views + privileges to restrict users. Single-table views with a key are updatable; multi-table/aggregate views are not.

1. Concepts — مفاهيم

File organization = how physical records are arranged on disk. Access method = how data is retrieved given that organization. We compare three types by their insert and search costs.

تنظيم الملف = كيف تُرتَّب السجلات على القرص. Heap: الإدخال سريع (بالنهاية) لكن البحث بطيء (خطّي). Sequential (مرتّب): البحث سريع بالبحث الثنائي log₂ b لكن الإدخال مكلف. Hash: البحث سريع جدًا على مفتاح التجزئة لكن القراءة المرتّبة غير فعّالة.

2. Ordered Files & Binary Search

Records are physically sorted on an ordering field (if it’s a key, it’s the ordering key). Binary search needs only ~log₂(n) block reads instead of a linear scan. The cost is insertion: about half the blocks must be read/rewritten to make room.

3. Hashed Files — ملفات التجزئة

Disk hashing = external hashing. Blocks are divided into M buckets; a record with key K goes to bucket i = h(K). Common function: h(K) = K mod M.

📘 Collisions
A collision occurs when records hash to the same bucket. Resolution methods:
  • Open addressing — probe the next free position in order (e.g. linear probing).
  • Chaining — keep overflow locations; add a pointer from the full bucket to the overflow record.
Keep a hash file 70–80% full: higher load → more collisions; lower → wasted space. h should distribute uniformly.

Drawbacks of static hashing: the fixed M is a problem as the file grows/shrinks, and ordered access is inefficient.

Dynamic & Extendible Hashing

These allow the number of buckets to grow/shrink. Both use the binary representation of h(K) to index a directory: in dynamic hashing the directory is a binary tree; in extendible hashing it’s an array of size 2^d (d = global depth). When a block fills, it splits and the directory expands — greatly reducing the need for a separate overflow area.

التجزئة على القرص اسمها external hashing: السجل يروح للدلو bucket رقم h(K)=K mod M. التصادم collision يُحلّ بـopen addressing (نبحث عن موقع فاضي) أو chaining (مؤشّر لموقع فائض). نُبقي الملف ٧٠–٨٠٪ ممتلئًا. التجزئة الديناميكية والقابلة للتوسّع تسمح بنمو الدلاء عبر دليل (شجرة ثنائية / مصفوفة بحجم 2^d) وتقسيم الكتل الممتلئة.
🧾 Chapter 12 Summary — الخلاصة
Heap files: fast insert, slow (linear) search. Ordered files: binary search (log₂ b) but costly inserts. Hashed files: near-instant key lookup via h(K)=K mod M, collisions handled by open addressing or chaining, kept 70–80% full; static hashing’s fixed M motivates dynamic/extendible hashing with a splitting directory.

Indexing & Physical Database Design

Textbook: Chapter 17 · Slides (Week 14) + Notes (Week 15)
🎯 Lecture Outline

1. What is an Index? — ما هو الفهرس؟

An index is an additional on-disk file (data structure) that provides a secondary access path to quickly locate records, without changing the physical placement of the data file. It’s a file of <field value, pointer> entries ordered by field value (an access path). Index files are much smaller than data files, so binary search on the index is fast.

2. Single-Level Ordered Indexes — الفهارس أحادية المستوى

TypeDefined onDense/SparseHow many
PrimaryOrdered file, on the ordering KEY field. One entry per block (the block anchor).Sparse (non-dense)At most one
ClusteringOrdered file, on a non-key ordering field. One entry per distinct value.SparseAt most one
SecondaryAny non-ordering field (data file unordered on it). One entry per record.DenseMany allowed
📘 Dense vs Sparse · key rules
Dense: one entry for every record. Sparse: entries for only some values (e.g. block anchors). A file has at most one physical ordering field → at most one primary or one clustering index (not both), but many secondary indexes. Secondary indexes must be dense (data isn’t ordered, so no block anchors).

3. Blocking Factor & Access Cost — معامل التجميع

📘 Formulas
Blocking factor Bfr = Block size B ÷ Record size R (records per block).
Number of blocks b = ⌈ r ÷ Bfr ⌉; binary search ≈ ⌈log₂ b⌉ block accesses; linear search ≈ b/2. 
-- Data file: R=100, B=1024, r=30000
Bfr = 1024 / 100 = 10 records/block
b   = 30000 / 10 = 3000 blocks
binary search = log2(3000) ≈ 12 accesses

-- Primary index on SSN: V=9, pointer P=6
RI  = 9 + 6 = 15 bytes/entry
BfrI= 1024 / 15 = 68 entries/block
b   = 3000 / 68 ≈ 45 index blocks
search = log2(45) ≈ 6 + 1 = 7 accesses   (vs 1500 linear, 12 ordered)

A dense secondary index on the same file has 30000 entries → 30000/68 ≈ 442 blocks → log₂(442)+1 ≈ 10 accesses (better than 1500 linear, worse than the primary index’s 7, because the data file isn’t ordered on that field).

4. Multilevel Indexes — الفهارس متعددة المستويات

Since a single-level index is itself an ordered file, we can build a primary index on the index — the first-level index, then a second level, a third, … until the top level fits in one block. The fan-out (fo) = the index blocking factor, so the search cost drops to log_fo(b). Total record access = (number of levels t) + 1.

-- Continuing the secondary index (fo = 68, b1 = 442):
b2 = 442 / 68 = 7
b3 = 7 / 68   = 1   ← top level
levels t = 3  →  total accesses = t + 1 = 4

The downside: every level is an ordered file, so insertion/deletion is hard → solved by dynamic multilevel indexes using B-trees and B⁺-trees (balanced tree structures). Other index types: hash index (fast exact-match, poor for ranges) and composite / multiple-key index (on several columns).

الفهرس ملف إضافي يوفّر مسار وصول ثانوي دون تغيير ترتيب البيانات. ثلاثة أنواع أحادية: Primary (على مفتاح الترتيب، sparse)، Clustering (على حقل ترتيب غير مفتاح)، Secondary (على أي حقل غير مرتَّب، dense، ويمكن تعدّده). الملف له فهرس primary أو clustering واحد فقط، لكن secondary متعدّد. معامل التجميع Bfr = B/R، وعدد الكتل b = r/Bfr، والبحث الثنائي log₂ b. الفهارس متعددة المستويات تبني فهرسًا على الفهرس وتقلّل التكلفة إلى log_fo(b)، وتُنفَّذ بـB/B⁺-Trees.
📝 Exam Tips
Primary & clustering = on the ordering field = sparse, at most one each. Secondary = on a non-ordering field = dense, many allowed. Know the formulas: Bfr=B/R, b=r/Bfr, binary search = log₂ b, multilevel = t+1 accesses.
🧾 Chapter 13 Summary — الخلاصة
Indexes are extra <value, pointer> files giving fast secondary access. Primary (sparse, ordering key) and clustering (sparse, non-key ordering) — one each; secondary (dense, any field) — many. Compute cost via Bfr=B/R, b=r/Bfr, binary search log₂ b. Multilevel indexes (B/B⁺-trees) reduce search to log_fo(b) and access to t+1 blocks.

  5. A LEFT OUTER JOIN of Customers & Stores on city — how many rows, and why?
  6. Conceptual difference between IN and EXISTS?
  7. Two mandatory conditions for 3NF?
  8. Course(course_id, instructor, phone) with course_id→instructor, instructor→phone: why not 3NF, and decompose it.
  9. Structural difference between 3NF and BCNF?
✅ Answers
  1. π(make, year+1)(Car) — projection selects columns & applies the transformation.
  2. σ(year=2015)(Car) — selection filters rows.
  3. Rename S’s attributes to match R (e.g. ρ). UNION requires union compatibility: same number of attributes, compatible types, matching names.
  4. σ filters rows (horizontal) by a condition; π selects columns (vertical) and removes duplicates.
  5. 8 rows — 6 inner-join matches + 2 unmatched left rows (Bob, Emily) padded with NULL.
  6. IN checks if a value matches any value in the result set; EXISTS checks if the (correlated) subquery returns at least one row and can stop at the first match.
  7. (1) Must be in 2NF; (2) no transitive dependency (no non-key depends on another non-key).
  8. Transitive dependency: phone depends on instructor (non-key), not directly on course_id → decompose into Course(course_id, instructor) and Instructor(instructor, phone).
  9. 3NF allows a non-prime attribute to depend on a superkey but forbids non-key→non-key; BCNF is stricter: every determinant must be a candidate key.

3. Self-Test — SQL (Set ops, Aggregation, Joins, Subqueries)

📝 Key MCQs & queries
  • Operator returning rows in both sets (no duplicates) → INTERSECT.
  • Use HAVING (not WHERE) to filter on an aggregated value.
  • NATURAL JOIN auto-joins on all same-named columns → risk of unintended matches.
  • LEFT OUTER JOIN → all left rows, NULLs for unmatched right columns.
  • EXISTS is TRUE when the subquery returns ≥ 1 row; a correlated subquery references the outer row and runs once per outer row.
-- Avg salary per dept, ≥3 employees and avg > 60000
SELECT dept_id, AVG(salary) AS avg_sal FROM Employees
GROUP BY dept_id HAVING COUNT(emp_id) >= 3 AND AVG(salary) > 60000;

-- Employees above company average (non-correlated subquery)
SELECT name, salary FROM Employees
WHERE salary > (SELECT AVG(salary) FROM Employees);

-- Departments with an employee earning > 80000 (EXISTS)
SELECT d.dept_name FROM Departments d
WHERE EXISTS (SELECT 1 FROM Employees e
              WHERE e.dept_id=d.dept_id AND e.salary>80000);
⚠️ Classic debugging trap
WHERE COUNT(emp_id) > 2 is wrong — WHERE can’t filter aggregates. Use HAVING after GROUP BY: 
SELECT dept_id, COUNT(emp_id) AS total_emp
FROM Employees
GROUP BY dept_id
HAVING COUNT(emp_id) > 2;
Common pitfalls: WHERE-vs-HAVING on aggregates · UNION (removes dups) vs UNION ALL · GROUP BY placement · forgetting FOR EACH ROW in triggers · assuming NATURAL JOIN is safe.
